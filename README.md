# SCM_LLM_Agent

LLM 에이전트가 활용하는 Context(C), Message(M), Tool(T)의 구성을 달리하여 공급망 의사결정을 비교하는 연구 코드입니다. **각 기간에 소매상 → 도매상 → 유통업자 → 공장 순서로 각자의 전체 과정을 끝냅니다.** Python 3.11 이상, 별도 패키지 설치 없이 실행할 수 있습니다. 설계 원본 Word 파일 없이도 아래 설명서와 코드로 현재 구현을 확인할 수 있습니다.

## 실행

이 폴더에서 PowerShell 또는 터미널을 열어 실행합니다. API 키는 기존 `OPENROUTER_API_KEY` 환경변수를 사용하며 결과 파일에 저장하지 않습니다.

```powershell
# 등록된 103개 조건을 확인합니다. API 호출 없음.
python -m scm list

# 실행 전 호출 수와 예산을 확인합니다. API 호출 없음.
python -m scm run --conditions C3M1T2 --seeds 123 --backend openrouter --output results/my_run --budget-usd 1 --dry-run

# 원하는 조건과 원하는 seed만 실행합니다.
python -m scm run --conditions C3M1T2 --seeds 123 --backend openrouter --output results/my_run --budget-usd 1

# 여러 조건을 같은 수요 seed로 비교합니다.
python -m scm run --conditions A C0M0T2 C3M1T2 --seeds 123 456 --backend openrouter --workers 3 --output results/comparison --budget-usd 2

# 저장된 응답과 checkpoint를 활용해 중단된 동일 실행을 재개합니다.
python -m scm run --conditions C3M1T2 --seeds 123 --backend openrouter --output results/my_run --budget-usd 1 --resume

# 유료 API 없는 소프트웨어 검사. mock 결과는 연구 성능이 아닙니다.
python -m unittest discover -s tests -v

# 완료된 실행만 조회합니다. 미완료 실행의 진행량·비용은 포함하지 않습니다.
python status.py results/my_run
```

Windows에서는 `Run-Experiment.ps1`도 사용할 수 있습니다. 조건·seed·backend를 직접 입력해야 하며, 실행 버튼만 눌러 전체 조건이 시작되는 기능은 없습니다. `--conditions`와 `--seeds`는 필수이며 seed 범위를 코드에 고정하지 않았습니다. 위 123/456은 사용 예시입니다.

`--objective cost` 또는 `--objective bullwhip`로 A와 일반 CMT 조건의 목적을 선택할 수 있습니다. 기본 목적은 공급망 전체 운영비용 최소화입니다. `D_cost`와 `D_bullwhip`의 목적은 이름대로 고정됩니다. 목적은 실행자가 선택하며 LLM이 바꾸지 않습니다. 서로 다른 목적은 별도 실행 폴더에 저장하세요.

```powershell
# 아래 두 명령은 목적 선택을 확인하는 dry-run으로, 유료 호출이 없습니다.
.\Run-Experiment.ps1 -Conditions A,C0M0T0 -Seeds 123 -Backend openrouter -Objective cost -DryRun
.\Run-Experiment.ps1 -Conditions A,C0M0T0 -Seeds 123 -Backend openrouter -Objective bullwhip -DryRun
# D 두 조건을 함께 선택할 때는 Objective를 생략하여 각자의 고정 목적을 유지합니다.
.\Run-Experiment.ps1 -Conditions D_cost,D_bullwhip -Seeds 123 -Backend openrouter -DryRun
```

현재 코드의 API 설정은 `google/gemini-2.5-flash-lite`, Google AI Studio Flex입니다. 일반 요금·다른 공급자로의 자동 변경은 허용하지 않습니다. 매 응답의 실제 모델·제공자·Flex를 검증하며 temperature=0.1입니다. 모델 seed와 reasoning 옵션은 보내지 않습니다.

**동일한 수요 seed를 사용하면 외부 고객 수요 경로와 공통 준비기간 상태가 동일하게 생성됩니다. 다만 LLM의 응답은 실행마다 달라질 수 있으므로, 최종 발주량과 성과지표까지 완전히 동일하게 재현되는 것은 보장하지 않습니다.** 이 설명은 동일한 코드·설정·실행 환경을 전제로 합니다. 상류 에이전트의 수주량은 하류의 실제 발주량으로 결정되므로, LLM 발주가 달라지면 상류 수주와 이후 재고·백로그도 달라질 수 있습니다. 중단된 동일 실행의 `--resume`은 저장된 응답을 재사용하는 기능이며, 새로 API를 호출해 실험을 반복하는 것과 구분합니다.

## 구현한 실험

| 요소 | 수준 |
|---|---|
| C0 / C1 / C2 | 현재 포함 상태 원자료 10 / 20 / 5기, 과거 기준·최종 주문량은 각각 9 / 19 / 4개 |
| C3 | 현재 D/I/B/P_pre 별도 + 현재 포함 10기 D/I/B/P_pre의 평균·표본 SD·최대·최소. 과거 주문량 및 주문 통계 없음 |
| M0 | 추가 메시지 없음. 실제 주문 거래는 전달 |
| M1 | 환경이 하류 현재 I/B/P_post/D 및 수주 10기 평균·표본 SD를 전달 |
| M2 / M3 / M4 | 정성적 근거 / 다음 2기 행동 계획 / 자유 메시지. 별도 LLM 호출, 출력 최대 300토큰 |
| T0 | 30기 수주로 LLM 자유 예측 |
| T1 / T2 | 고정 선형회귀를 LLM 직접 계산 / 코드 계산 |
| T3 / T4 | C/M으로 예측법을 고르고 LLM 직접 계산 / 코드 계산 |

후보는 LR30, 이동평균30, SES(alpha=0.3)입니다. SES는 매 30기 창의 최초 관측으로 초기화합니다. 예측 대상은 자신의 수주 D[t+1], D[t+2]입니다. T3는 LLM이 선택한 방법의 **공식을 제공받고 직접 계산**하며 T4는 코드가 계산합니다. 예측의 30기 자료나 대화가 최종 주문 프롬프트로 넘어가지 않습니다. 일반 CMT와 D의 최종 프롬프트에는 C, 수신 M, 당기 기준 주문량이 주어지며, 각 정보의 의미와 세 정보를 종합하라는 지시를 명시합니다. M0~M4는 수신 정보의 대안적 수준이며 모두를 함께 받는 것이 아닙니다.

일반 100조합의 기준 주문량은 `max(0, forecast_h1 + forecast_h2 + SS - (I+P_pre-B))`, SS=0입니다. `Q_base_raw`는 정수 반올림·상한 보정 전의 값이고 `Q_base`는 보정 후 참고량입니다. raw는 과거 원자료를 뜻하지 않습니다.

**전체 100조합 + 별도 A + D_cost + D_bullwhip = 103조건**입니다. A와 C0M0T0는 서로 다른 조건입니다.

- A: 예측·도구·OUT·당기 기준 주문량 없이 C0와 당기 수주 D만으로 LLM이 최종 발주를 결정합니다. D는 C0의 당기 D와 동일하며 중복 수주가 아님을 명시합니다. 평가기간의 Q_base와 예측 기록은 null입니다. 공통 준비기간의 과거 기준·최종 주문 이력은 C0 규칙에 따라 유지되며 평가기간 중 과거 Q_base는 null이 됩니다.
- C0M0T0: C0/M0에 더해 별도 LLM이 30기 수주로 예측하고, 환경이 OUT 기준 주문량을 계산한 뒤 최종 LLM이 결정합니다.
- D_cost / D_bullwhip: 모두 C0+M4를 사용합니다. D_cost는 LR30의 다음 기 예측, D_bullwhip은 수주 평균30을 이용한 EOQ를 직접 참고값으로 주며 OUT을 적용하지 않습니다.

E와 Holt는 구현 범위에서 제외했습니다. C3의 주문 이력 제외와 현재 M2/M3의 메시지 내용은 이번 수정에서 변경하지 않았습니다.

### 공동연구자가 확인할 남은 설계 선택

현재 논의 중인 선택은 아래 세 항목입니다. **현재 구현**은 실행 가능한 기존 정의이고, **검토 중인 대안**은 아직 적용하지 않은 제안입니다. 103조건 구성과 별도 A 정의는 확정되어 있습니다.

| 항목 | 현재 구현 | 아직 결정할 부분 |
|---|---|---|
| C3 | 현재 D/I/B/P_pre + 각 변수의 최근 10기 통계, 과거 기준·최종 주문 이력 제외 | 이 구성을 유지할지, C0와 정보 범위를 맞출지, 또는 주문 이력을 뺀 C0 보조조건을 일부 M/T에서 비교할지 |
| M2 | 당기 확정 주문의 이유를 짧은 정성 문장으로 전달 | 자유문장과 정해진 이유 항목 선택 중 어떤 형식을 사용할지 |
| M3 | 다음 두 기간의 발주 행동 계획을 두 문자열로 전달, 정성·정량 표현 허용 | 이 형식을 유지할지, 다음 두 기간의 계획 발주량 두 정수만 전달할지 |

C0와 현재 C3를 직접 비교하면 상태 표현의 요약뿐 아니라 과거 주문 이력의 제거도 함께 달라집니다. 원자료와 통계 표현만 비교하려면 제공 변수와 기간을 맞춘 비교가 필요합니다. 보조조건을 채택하면 현재 103조건 외의 추가 실험이며, 아직 등록하지 않았습니다.

수치형 M3를 채택할 경우의 제안은, 당기 주문을 확정한 뒤 LLM이 자신에게 허용된 C·수신 M·당기 기준/최종 주문량·발주 후 파이프라인으로 다음 두 기간의 계획량을 자율적으로 정하는 것입니다. 계획을 생성하는 고정 공식이나 실제 미래 정보는 제공하지 않습니다. 환경은 정수·수량 범위를 검사하며, 계획량이 향후 실제 주문으로 자동 실행되지는 않습니다. **이 수치형 M3는 아직 구현하지 않았습니다.**

### 결과 파일의 raw와 수량 용어

`Q`는 발주량, `base`는 최종 판단에 제공하는 기준량, `final`은 LLM 판단을 거쳐 실제 실행하는 주문을 뜻합니다. **수량 변수의 `_raw`는 해당 단계에서 수량 보정하기 전 기록한 값**이라는 뜻입니다. 반면 C의 `representation="raw"`는 통계로 요약하지 않은 기간별 상태 원자료라는 뜻입니다. 필드별로 무엇을 보정하기 전인지 아래와 같이 구분합니다.

| 코드·결과 필드 | 함께 사용할 한국어 설명 | 읽는 방법 |
|---|---|---|
| `Q_base_raw` | 정수·상한 보정 전 기준 주문량 | 일반 CMT에서는 OUT 식의 `max(0, ...)`까지 적용된 계산값. 이후 반올림·상한 보정을 거쳐 `Q_base`가 됨. D에서는 각 참고량 계산값 |
| `Q_base` | 최종 판단에 제공하는 기준 주문량 | `Q_base_raw`를 공통 정수·범위 규칙으로 보정한 값. 이 값 자체가 실제 발주로 확정되는 것은 아님 |
| `Q_final_raw` | LLM이 제안한 보정 전 최종 주문량 | 정상 응답에서 추출한 `order_quantity`. 수량 보정 후 `Q_final`로 실행 |
| `Q_final` | 실제 실행한 최종 발주량 | 물류 갱신과 발주 비용 계산에 사용하는 정수 수량 |
| `forecast_raw` | 예측 단계에서 기록한 출력값 | LLM 정상 예측은 환경의 음수 보정 전 응답값. 코드 예측·예측 실패 대체는 도구 내부에서 이미 음수를 0으로 보정한 결과이므로, 항상 수학식의 무보정 결과를 뜻하지는 않음 |
| `fallback_quantity_raw` | 실패 대체 발주량의 보정 전 값 | A의 주문 호출이 최종 실패했을 때 사용하는 당기 수주량. 보정 후 실제 발주는 `Q_final`에 기록 |
| `raw_output` | 모델 출력 원문 문자열 | API 응답에서 추출한 모델 출력 텍스트로, JSON 해석·필드 검증 전의 기록. 전체 HTTP 응답을 뜻하지 않으며 수량 하나도 아님 |
| C의 `representation="raw"` | 기간별 상태·주문 원자료 | C0/C1/C2가 D/I/B/P_pre와 허용된 과거 주문 이력을 개별 기간 기록으로 제공한다는 표시. 각 상태는 이미 당기 입고·출고를 반영한 값 |

예를 들어 OUT 계산으로 `Q_base_raw=12.6`이 나오면 현재 규칙에서 `Q_base=13`을 최종 판단에 제공합니다. LLM이 `Q_final_raw=9.5`를 제안하면 `Q_final=10`을 실제 발주합니다. 0.5는 위쪽 정수로 반올림하며 현재 발주 범위는 0~100입니다. 따라서 보정 전 제안이 120.2라면 실제 발주는 100입니다. `raw`를 함께 보존하는 이유는 계산·제안 단계와 환경의 수량 보정이 결과에 각각 어떤 영향을 주었는지 확인하기 위해서입니다.

A는 당기 기준 주문량을 만들지 않으므로 `Q_base_raw`와 `Q_base`가 모두 `null`입니다. 주문 호출이 최종 실패하면 유효한 LLM 제안이 없으므로 `Q_final_raw=null`이고, 실제 대체 발주량은 `Q_final`과 실패 기록을 함께 확인해야 합니다. **`null`은 값이 없다는 뜻이며, 0개 발주와 구분합니다.**

## 물류·초기화

- 0기: 각 단계 I=0, B=0, 미입고 발주잔량 P=20; 1·2기에 10씩 도착.
- -29~0기 수주 이력은 각 10. 1~30기는 규칙 기반 LR30+OUT으로 운영하며 API 호출 없음.
- 수요는 독립 정규분포 N(10,3²)를 `random.Random(seed).gauss`로 생성한 뒤 비음수 half-up 정수화합니다. 수요 상한은 없습니다.
- 같은 seed의 수요 경로와 30기 종료 물류 상태·예정 입고·이력을 모든 조건에 복제합니다. 31기부터 상태를 초기화하지 않습니다.
- C의 P는 입고 차감 후·당기 주문 전 P_pre. M1의 P는 당기 주문을 더한 P_post.
- P에는 상류 미출고 backlog도 포함합니다. 실제 운송 예정표는 별도이며, 실제 출고한 물량만 2기 뒤 도착합니다. 공장 외부 생산은 무제한이며 공장 발주가 2기 뒤 입고됩니다.
- 기존 backlog를 신규 수요보다 먼저 충족합니다. 매 기간 말 `P = 실제 운송중 물량 + 상류 backlog`를 검사합니다.

수식의 i는 현재 에이전트, t-1은 같은 에이전트의 직전 기간입니다. 출고량은 `X[i,t] = min(I[i,t-1] + A[i,t], B[i,t-1] + D[i,t])`입니다. 하류는 i-1이고, 소매상을 제외하면 `D[i,t] = Q_final[i-1,t]`입니다. 직전 기간과 이웃 에이전트를 구분합니다.

## 공통 G와 기록

수량은 half-up 반올림 후 발주만 0~100으로 보정하고 원값·보정 여부를 기록합니다. 예측은 연속값으로 유지하며 음수만 0으로 보정합니다. JSON 필드·자료형·유한성·선택 후보를 검증합니다. 숫자 enum 대신 일반 숫자 필드를 사용합니다.

단계별 실패에는 최초 요청 후 **재시도 최대 1회**만 허용합니다. 전송·형식·메시지 검증 실패가 같은 재시도 예산을 공유합니다. 예측/선택 최종 실패는 코드 LR30, 일반 CMT/D의 최종 주문 실패는 당기 기준 주문량, 메시지 실패는 빈 메시지로 대체합니다. **A의 최종 주문 실패는 당기 수주량을 공통 수량 규칙으로 보정하여 대체**하고 `fallback_policy=current_request`로 기록합니다. A는 실패해도 예측이나 OUT을 실행하지 않습니다. 인증·결제·설정·물리 보존식 오류는 실행을 중단합니다. T1/T3의 유효한 계산값이 코드 정답과 달라도 값을 고쳐주지 않고 차이를 기록합니다.

M2의 숫자·명시적인 향후 행동 표현은 검사와 재시도 대상입니다. 모든 자연어 의미 제약을 자동으로 완벽하게 검사할 수는 없으므로 원문 메시지를 보존합니다. 현재 M3는 두 기간의 문자열 계획 필드를 분리하며, 정성·정량 표현 모두 허용합니다. 계획은 향후 발주를 강제하지 않고 다음 기 자신의 C에 다시 주입되지 않습니다. M2/M3의 더 엄격한 내용 분리는 아직 제안 단계입니다.

각 실행은 `results/<실행폴더>/episodes/<조건>__<목적>__seed-<값>/`에 다음을 저장합니다.

- `manifest.json`: 조건·모델·설정·소스 해시
- `api_calls.jsonl`: 모든 실제 시도의 입력·응답·토큰·비용·실제 모델/라우트·오류
- `checkpoint.json`: 완료한 결정까지의 물류 상태와 다음 수신 메시지
- `periods.csv`, `periods.json`: 모든 평가 행과 C/M/T·결정·실패 진단
- `summary.json`: 완료된 100기의 지표
- `failure.json`: 중단된 경우 원인. 중단 결과를 완주 결과로 취급하지 않음

`failure.json`은 재개 후에도 과거 중단 이력으로 보존합니다. 현재 완주 여부는 `summary.json`과 배치의 `batch_status.json`으로 확인합니다. JSON snapshot 교체가 일시적인 파일 잠금으로 실패하면 최초 시도를 포함해 최대 6회, 합계 최대 1.25초 대기하며 재시도합니다. 계속 실패하면 이전 checkpoint를 유지하고 오류를 보고합니다. 다른 저장 오류는 즉시 보고합니다. 이 저장 재시도는 LLM 재시도와 별개이며 API를 다시 호출하지 않습니다. `status.py`는 실행 중 파일을 읽지 않아 진행 조회가 파일 교체를 방해하지 않도록 했습니다.

재개 시 동일 소스·설정이 필요하며, 완료된 API 응답은 journal에서 재사용합니다. 이전 호출을 재생한 결정의 전체 지연시간은 `null`로 구분하고 원래 호출별 지연시간은 유지합니다. 운영체제 강제종료로 `.running.lock`이 남으면 해당 프로세스가 종료되었는지 확인한 후 그 잠금 파일만 제거해야 합니다. 소스 변경 후에는 새 결과 폴더를 사용합니다.

## 평가지표

주 지표 `cost_per_period`는 4단계의 `(재고 + backlog + 최종 발주량 + 양수 발주 여부)`를 31~130기 동안 합산한 뒤 **100으로 나눕니다**. 네 단가는 모두 1이며 API 비용은 별도입니다. 즉시 충족률은 신규 고객 수요를 같은 기간에 충족한 비율입니다. `global_bullwhip`은 네 단계 최종 주문량의 표본 SD/평균(CV)을 **곱한 값**입니다. 주문 관측이 2개 미만이거나 평균이 0이면 해당 CV를 null로 기록하며, 하나라도 CV가 정의되지 않으면 global_bullwhip도 null입니다.

모든 예측·선택·주문·메시지·재시도 호출의 토큰과 보고 비용을 합산합니다. 사용량이 보고되지 않으면 0으로 바꾸지 않고 알려진 부분 합계와 누락 건수를 구분합니다. API 예산 제어에는 미보고 호출을 보수적 추정액으로 반영합니다. 의사결정 지연시간은 예측 시작부터 주문·송신 메시지 확정까지입니다.

`--evaluation-periods`의 기본값은 100이며 다른 값은 진단용입니다. 모의 실행과 짧은 동작 점검을 정식 성능 결과에 섞지 않습니다. 새 연구 결과에는 조건·반복 수·상호작용·다중비교를 고려한 사전 분석 계획이 필요합니다.
